# PRレビューコメント対応

引数としてPR番号またはPR URLを受け取る。省略された場合、手順1のスクリプトが現在のブランチに紐づくPRを自動検出する（`gh pr view`ベース）。ユーザーへの質問で立ち止まる必要はない。自動検出できなかった場合はスクリプトがエラー終了するので、その時点でPR番号またはPR URLをユーザーに尋ねる。

GitHub PRのレビュー指摘に対応する。ここでいう「対応」は、コメントを読んで終わりではなく、
実際にコードを直し、コミットし、PRに反映するところまでを指す。

対象はインラインコメント（ファイル・行に紐づくコメント）だけではない。
**レビューのサマリコメント**（Approve/Comment/Request changesの総評欄。GraphQLでいう `PullRequestReview.body`）にも指摘が書かれることがある。
特に、行番号を一意に確定できない指摘（テスト全体の構造、設計方針、複数箇所にまたがる話など）は
インラインに置けないためサマリ側に落ちてくる。ここを見ないと指摘を丸ごと取りこぼす。

## 実行モード

引数に `--non-interactive` が含まれる場合は**非対話モード**として振る舞う（`claude -p` などユーザーへ対話的に承認を取れない実行を想定）。含まれなければ通常の**対話モード**。

- モード判定はこの引数フラグの有無だけで行う。環境変数（`CLAUDE_CODE_ENTRYPOINT` など）で非対話かどうかを推測しない（確実に判定する公式手段がなく不安定なため）。
- `--non-interactive` はPR番号/URLとは独立した引数であり、順序は問わない。手順1のスクリプトに渡す位置引数はPR番号/URLのみなので、`--non-interactive` はスクリプトへ渡さず、このSKILL側で読み取って手順4の分岐に使う。

両モードで異なるのは手順4（PR本文の更新）だけ。それ以外の手順（PR自動検出・修正・コミット・push）はどちらのモードでも同じく自動で進めてよい。

## なぜHide/解決状態で絞り込むのか

PRには「もう見なくていい」コメントが溜まっていることが多い：
- スパムや誤検知としてMinimize（Hide）されたコメント
- 既に対応済みでresolveされたスレッド

見なくていいコメントまで拾うと、本人が意図的にHideしたものを蒸し返したり、無関係な修正が紛れ込んだりする。
この絞り込み（Hide/解決の判定とページング）は判断の要らない定型処理なので、手順1のスクリプトに切り出してある。

ただし絞り込みの基準は2種類で異なる：

- **インラインコメント**: スレッドが未解決（`isResolved == false`）かつコメントがHideされていない（`isMinimized == false`）
- **サマリコメント**: Hideされていない（`isMinimized == false`）ことだけが基準。レビュー本文には
  resolveに相当する状態がAPI上存在しないため、「対応済みかどうか」をスクリプト側で判定できない

この非対称性の帰結として、**サマリコメントは対応済みでも再実行のたびに再提示される**。
対応済みの指摘が混ざっている前提で手順2の調査を行い、既に直っているなら「対応済み」としてスキップすること。
なお、対応が済んだサマリコメントをユーザーがHideしておけば次回以降は除外される（対応完了時にその旨を伝えてもよい）。

## 手順

### 1. 未対応コメントを抽出する

スクリプトはこの `SKILL.md` と同じディレクトリの `scripts/fetch-unresolved-comments.sh` にある。

```bash
bash "<この SKILL.md のあるディレクトリ>/scripts/fetch-unresolved-comments.sh" <PR番号 または PR URL>
```

引数を省略すると現在のブランチに紐づくPRを対象にする。owner/repoはPR URLから抽出するか、無ければ現在のリポジトリから自動検出する。

stdout に対象コメントだけを整形済みJSON配列で返す（`reviewThreads`・`reviews` のページングも内部で処理済み）:

```json
[
  { "type": "inline",  "id": "...", "databaseId": 123, "path": "...", "line": 10,
    "author": "...", "authorType": "User", "url": "...", "body": "..." },
  { "type": "summary", "id": "...", "databaseId": 456, "path": null, "line": null,
    "author": "...", "authorType": "Bot", "url": "...", "state": "COMMENTED",
    "submittedAt": "...", "body": "..." }
]
```

`type` でインラインコメントとサマリコメントを見分ける。stderrには `対象 N 件（インライン X 件 / サマリ Y 件）` が出る。
`authorType` は `User`（人間）か `Bot`（GitHub App）。`author`（login）だけでは bot を判別できない
（例: `github-actions[bot]` の login は `github-actions`）ため、書き手の種別はこちらで見る。

抽出できたら、対象件数と各コメントの要旨（ファイル・指摘内容）を短く報告してから着手する。
このとき、**サマリコメントはJSON上1件でも中に複数の指摘が含まれうる**ので、件数だけでなく
中身を読んで指摘を個別に数え上げて報告する。
0件だった場合はそこで完了を伝えて終わる（無理に何かを直そうとしない）。

### 2. 各指摘を実際に調査してから直す

レビューコメント、特にbotによる自動レビューは、提案（`suggestion`ブロックなど）をそのまま鵜呑みにできるとは限らない。
指摘が指しているファイル・シンボルが**現在のコードにまだその形で存在するか**、提案されている修正先が
**実際に正しい移行先か**を、そのつど調べる。具体的には：

- 指摘が「参照切れ」「移行漏れ」を主張しているなら、`grep`/`git log`で参照元と移行先の実体を確認する
- 指摘が特定の関数・設定・ファイルを名指ししているなら、それが現在も同じ名前・同じ場所にあるか確認する
- コメントに `suggestion` ブロックが付いている場合も、周辺の実装や命名規則と整合するか一度目で確認してから採用する（コピペで即採用しない）

調査の結果、指摘が的外れ・スコープ外（例: 過去の設計判断の記録であって実害のあるリンク切れではない）と判断した場合は、
その理由を添えて対応をスキップしてよい。全部を無理やり直す必要はない。

#### サマリコメント（`type: "summary"`）の読み方

サマリコメントは1件の中に複数の指摘が混ざっていたり、指摘以外の情報が大半を占めていたりする。
本文を読んで、**対応すべき指摘だけを取り出す**こと。

- 指摘でない部分は対応対象にしない。例: 変更内容の要約・walkthrough、シーケンス図、
  レビュー結果の総括（「LGTM」など）、bot の署名行やバッジ画像、CIの自動レポート
- `<details>` で折りたたまれたブロックの中に指摘が入っていることがある。折りたたみも開いて読む
- 「インラインで N 件指摘し、行番号未確定の M 件をここに記載します」のような前置きは、
  **ここに本文でしか読めない指摘がある**というシグナル。この種の文が出てきたら本文を最後まで読む
- サマリの指摘は行に紐づかない分、対象箇所を自分で特定する必要がある。
  本文中のファイル名・シンボル名を手がかりに実コードを開いて確認してから直す
- 同じ指摘がインラインコメントとサマリの両方に書かれていることがある。
  重複に気づいたら1件として扱い、二重に直さない
- `state` と `submittedAt` は「既に決着した指摘」を見分ける手がかりになる。
  `state` が `DISMISSED` のレビューや、同じ書き手による後続レビューが `APPROVED` になっている場合、
  その指摘は既に解消している可能性が高い。ただし推測で片付けず、実コードを見て確認してからスキップする

#### 指摘どうしが矛盾している場合

同じ箇所に複数のコメントが付き、内容が食い違うことがある（典型は、botの指摘に対して人間のレビュアーが
「それは誤りで、直すべきは別の箇所だ」と返しているケース）。この場合は次の順で優先する。

1. **人間のレビュアーの判断を、botの指摘より優先する**（`authorType` が `User` か `Bot` かで見分ける）
2. 同じ書き手なら、`submittedAt` が新しいものを優先する（後の投稿が前の投稿を訂正していることが多い）
3. それでも判断がつかなければ、実コードを読んでどちらが事実に合うかで決める

どちらを採用したか、なぜもう一方を採らなかったかは最後の報告に含める。

### 3. 修正・コミット・push

手順2で全件スキップし、修正対象が0件になった場合はこの手順を省略し、次の「対応が終わったら」に進む。

- コミットの単位はファイル数ではなく**関心事の一致度**で決める。同じ問題・同じ意図に属する修正はファイルをまたいでいても1コミットにまとめ（例:「廃止されたパスへの参照をすべて新パスに直す」）、無関係な指摘への修正がたまたま同じファイルに集まった場合は分ける
- コミットメッセージはそのリポジトリの既存コミット（`git log`）のスタイルに倣う
- 修正・コミット・pushはここまで自動で進めてよい。ユーザーに都度確認を挟む必要はない

### 4. PR本文への反映

手順3を省略した場合（追加コミットが0件）は、この手順も省略する。

追加コミットによってPRの変更内容が増えた場合、既存のPR本文に反映漏れが出ることがある。
base branchとの `git diff`/`git log`（`base..HEAD`）からPR全体の変更点を洗い出し、
本文に反映すべき内容があるか判断する。反映すべき内容がなければこの手順は何もせず終える。
反映すべき内容がある場合の扱いは実行モードで分岐する。
追記の粒度は、コミット単位（＝関心事）ごとに1〜2行の要約でよい。詳細な理由や調査過程まで書き込む必要はない。
タイトルは全体を的確に要約できていれば変更不要のことが多い。

- **対話モード**: 反映すべき内容を**更新前にユーザーに提示して承認を取り**、承認後にPR本文を更新する（PR本文の更新は外向きの操作なので、承認なしに自動で書き換えない）。
- **非対話モード（`--non-interactive`）**: 承認を取れないためPR本文は書き換えない。代わりに反映すべき内容をPRにコメントとして投稿する。コメント本文の冒頭に、これがPR本文への反映提案であり非対話実行のため自動投稿したものである旨の短い前置きを付ける。

  ```bash
  gh pr comment <PR番号 または PR URL> --body "<提案本文>"
  ```

## 対応が終わったら

- どのコメントに対応し、どれをスキップしたか（理由付きで）を簡潔にまとめる。
  サマリコメント由来の指摘は、そのサマリ内のどの指摘なのかが分かるように書く
- サマリコメント由来の指摘に対応した場合、そのサマリコメントをHideしておけば次回以降は抽出対象から外れる旨を添える
  （サマリコメントにはresolve状態がないため、Hideしない限り再実行で再提示される）
- commitのSHA・件名、PRのURLを報告する。追加コミットが0件だった場合（抽出0件、または全件スキップ）は、SHA・件名の欄を「新規コミットなし」と記載し、対象PRのURLのみ添える
- 非対話モードで手順4のPR本文反映提案コメントを投稿した場合は、そのコメントURL（取得できなければ投稿した旨）も報告に含める
