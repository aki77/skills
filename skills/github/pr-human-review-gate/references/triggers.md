# 人間レビュー必須トリガー集 (T1〜T8)

このファイルは、PR に **人間レビューが必要** と判断する 8 つのトリガー T1〜T8 を定義する。各トリガーには「含まれる例」「含まれない例」「チェックポイント」「なぜ人間が見るべきか」を併記する。

## このファイルの読み方 (重要)

**「含まれない例」は「含まれる例」と同じ重み、あるいはそれ以上の重みで読むこと。**

このゲートの価値は、8 トリガーに該当しない PR を `optional` に通すことで生まれる。トリガーの領域に「隣接している」だけの変更 (認可コードのリネーム、金額の表示フォーマット変更、既存パターンに沿った新機能追加など) を `required` に倒し始めると、ほぼすべての PR が `required` になり、ゲートが何も選別しなくなる。「含まれない例」はその防波堤である。

判定は次の形で行う: **「T<N> の、このチェックポイントに、このファイルのこの変更が該当する」と名指しできるか。** 名指しできないものは該当しない。名指しできるなら 1 件でも `required`。

各トリガーを見るときの順序:

1. 「含まれる例」に当たるか
2. 当たりそうなら「含まれない例」に当たっていないか
3. 「チェックポイント」の問いに答えられるか (答えが取れないなら、それは pending 条件を満たすかを別途検討する)

ベース: [レビューリードタイム改善のためのPR分類 (SHE Tech Blog, 2026)](https://zenn.dev/she_techblog/articles/937836550dfdf3)

## T1: `control_plane_change` 統制系変更

レビュー・審査・CI・ブランチ保護など、**統制の仕組みそのもの**に触れる変更。

- 含まれる例:
  - CI ワークフローから必須チェック (テスト・lint・型検査・セキュリティスキャン) を削除・スキップ・`continue-on-error` 化する変更
  - ブランチ保護設定、必須レビュワー数、CODEOWNERS の緩和
  - このゲート自身や自動 Approve の判定ロジック・許可リストの変更
  - デプロイ承認ステップの削除、手動 approve gate のバイパス
  - lint/型検査の除外設定 (`ignore` パス、`rubocop:disable`、`@ts-ignore`) を広い範囲に追加する変更
- 含まれない例:
  - CI にチェックを**追加**する変更 (統制が厚くなる方向は該当しない)
  - CI の実行時間短縮 (キャッシュ追加、並列化、不要ステップ削除でチェック内容は同一)
  - CI 上の Node/Ruby などランタイムバージョンの引き上げ
  - lint ルールを**厳しく**する変更、`rubocop:disable` を 1 箇所削除する変更
  - ワークフローファイルの YAML 整形・コメント追加・ジョブ名変更
- チェックポイント: **「この変更後、今より少ないチェックでマージ/デプロイできるようになるか」**。答えが No なら該当しない。増える方向・同じままの変更は非該当。
- なぜ人間が見るべきか: 統制を緩める変更は、以降のすべての PR の安全性の前提を書き換える。AI がこの変更を通すと、自分自身の判定の土台を自分で崩せてしまう。

## T2: `irreversible_operation` 不可逆操作

実行後に取り消せない操作 — データの物理削除、外部への送信、課金など。

- 含まれる例:
  - `destroy_all` / `delete_all` / `DROP TABLE` / `TRUNCATE` / ファイル削除など、復元経路のない削除処理の新規追加
  - カラム削除やデータ移行を伴う破壊的マイグレーション (down が書けない・データが失われる)
  - メール・プッシュ通知・SMS など、外部ユーザーへ送信され取り消せない処理の新規追加や送信対象の拡大
  - 決済・請求・ポイント付与など、金銭が動く外部 API 呼び出しの新規追加
  - 論理削除から物理削除への切り替え
- 含まれない例:
  - 論理削除 (`deleted_at` の更新、`discard`、状態カラムの変更) の追加 — revert とデータ復旧が可能
  - 既存の削除処理のリファクタリング (呼び出し条件・対象範囲は同一)
  - 追加のみのマイグレーション (テーブル/カラム/インデックスの追加、nullable での追加)
  - テストコード・開発用 seed・ローカル専用スクリプト内の削除処理
  - 既存メール送信の文面変更やテンプレート差し替え (送信条件・宛先は同一)
- チェックポイント:
  1. **「この PR を revert すれば、実行済みの影響も元に戻るか」**。戻るなら非該当。
  2. 削除処理がある場合、Grep で復元経路 (論理削除カラム、アーカイブテーブル、バックアップ取得、`paranoia`/`discard` 等の gem) の有無を確認する。復元経路があれば非該当。
- なぜ人間が見るべきか: 他のバグは修正して再デプロイできるが、消えたデータと送信済みの通知は取り戻せない。誤りのコストが構造的に非対称。

## T3: `security_boundary_change` セキュリティ境界

認証・認可・権限チェックなど、**誰が何にアクセスできるか**の境界の変更。

- 含まれる例:
  - 認可チェック (`before_action`、policy、guard、ミドルウェア) の削除、または条件の緩和
  - 権限判定の真理値表が変わる変更 (`&&` → `||`、否定の反転、条件の追加/削除)
  - 公開エンドポイントの追加、`skip_before_action :authenticate` の追加
  - スコープの拡大 (自分のリソースのみ → 同一組織のリソースも、admin 限定 → 一般ユーザーも)
  - 認証方式・トークン検証・セッション管理・CORS 許可オリジン・CSP の変更
  - シークレットの取り扱い変更 (ログ出力、環境変数からハードコードへ、等)
- 含まれない例:
  - 認可メソッドのリネーム、認可コードのファイル移動、ガード節への変換 — **真理値表が同一なら非該当**
  - 認可チェックの**追加** (これまで無かった場所に権限確認を入れる) — 境界が狭まる方向
  - 権限判定のテスト追加
  - 認可エラー時のメッセージ・リダイレクト先・HTTP ステータスの変更 (許可される集合は同一)
  - 認可ロジックに触れない画面/機能の追加で、既存の認可を通常どおり経由しているもの
- チェックポイント: **「この変更で、誰が何にアクセスできるかの集合が広がるか」**。変更前後で許可される (主体 × リソース) の組を比べ、広がるなら該当。狭まる・同一なら非該当。真理値表が同じことが diff から追えるかを実際に確認する (「認可ファイルに触っているから」は理由にならない)。
- なぜ人間が見るべきか: 権限の穴は攻撃者に発見されるまで無症状で、テストも CI も通る。「意図した緩和なのか事故なのか」は仕様の意図を知る人間しか判定できない。

## T4: `personal_data_flow_change` 個人情報フロー

個人情報・機微情報の取得・保存・出力の**経路**の変更。

- 含まれる例:
  - 個人情報を保存するカラム/テーブルの新規追加 (氏名・住所・電話・生年月日・決済情報・health/センシティブ属性など)
  - 個人情報を外部サービスへ送る経路の追加 (分析ツール、外部 API、CSV エクスポート、Webhook ペイロードへの追加)
  - ログ・エラートラッカー・監査ログへ個人情報を出力する変更
  - 個人情報を含むレスポンスフィールドの追加、他ユーザーの個人情報が見える画面の追加
  - マスキング・暗号化・匿名化処理の削除や緩和
- 含まれない例:
  - すでに保存済み・出力済みの個人情報を、同じ経路の中で扱うだけの変更 (表示位置の移動、フォーマット変更、並び替え)
  - マスキング・暗号化を**追加**する変更、ログから個人情報を除去する変更
  - 個人情報を含まないデータ (集計値、ID のみ、公開情報) の経路追加
  - 個人情報を扱うファイルのリファクタリング・リネーム (取得元・保存先・出力先は同一)
  - テストフィクスチャ内のダミー個人情報の追加・変更
- チェックポイント: **「個人情報の取得元・保存先・出力先のいずれかが新しく増えるか」**。3 つのどれも増えないなら非該当。増える場合は、その個人情報が既存の経路で扱われていた種類かを Grep で確認する。
- なぜ人間が見るべきか: 個人情報の流れは法令・プライバシーポリシー・利用者への説明と整合していなければならない。コードの正しさとは別軸の判断であり、diff からは読み取れない。

## T5: `external_contract_change` 外部契約

外部の利用者と交わした取り決め — API レスポンス形式、Webhook ペイロード、公開スキーマ、共有ライブラリの公開インターフェース — の変更。

- 含まれる例:
  - 公開 API / Webhook のレスポンスからフィールドを削除、名称変更、型変更、必須化
  - エンドポイントの削除・URL 変更、リクエストパラメータの必須化
  - 公開スキーマ (GraphQL / OpenAPI / protobuf) の破壊的変更
  - 別リポジトリ・別チーム・サードパーティが利用するライブラリの公開関数のシグネチャ変更
  - 共有データストア (他サービスも読むテーブル、キュー、S3 のファイル形式) のフォーマット変更
- 含まれない例:
  - レスポンスへのフィールド**追加** (既存の利用者は無視できる — 後方互換)
  - 任意パラメータの追加、デフォルト値が既存挙動と一致するオプション追加
  - リポジトリ内からのみ呼ばれる関数のシグネチャ変更 (呼び出し元がすべて同一 PR で更新されている)
  - 内部実装の変更で、外部から見た入出力が同一のもの
  - 未リリース・フラグ OFF・利用者ゼロが確認できているエンドポイントの変更
- チェックポイント:
  1. **「この契約の利用者はリポジトリの外にいるか」**。Grep で参照箇所を洗い、すべてリポジトリ内で同一 PR 内に閉じているなら非該当。
  2. 外にいる場合、**「後方互換か」**。追加のみ・任意のみなら非該当。
  3. 1 が Grep で確定できない (外部利用者の有無が分からない) 場合は、pending の 3 条件を満たすかを判断する。
- なぜ人間が見るべきか: 壊れるのは自分のリポジトリの外であり、CI もテストも影響を検出できない。移行期間・告知・バージョニングの判断は人間の調整事項。

## T6: `architectural_precedent` 新規パターン導入

コードベースに前例のない実装パターン・技術・レイヤー構造の持ち込み。

- 含まれる例:
  - コードベース初出のライブラリ/フレームワークの導入 (既存の同種ライブラリを置き換える場合を含む)
  - 初出のアーキテクチャ要素 (キャッシュ層、メッセージキュー、バックグラウンドジョブ基盤、状態管理ライブラリ、新しいデータストア) の追加
  - 既存の慣行と異なる方式での実装 (既存が全部 Service クラスなのに初めて Interactor を導入する、等)
  - 新しいディレクトリ階層・レイヤーの新設
- 含まれない例:
  - 既存パターンに沿った実装の追加 (既存に 20 個ある Service クラスの 21 個目、既存と同じ書き方のジョブ追加)
  - 既存ライブラリの新しい API を使うだけの変更 (ライブラリ自体は導入済み)
  - パッチ/マイナーバージョンアップ
  - ファイル数や行数が多いだけの変更 (規模は新規性ではない)
  - 自分がその技術に馴染みがないだけで、コードベースには前例がある変更
- チェックポイント: **判定前に必ず Grep/Glob で類似実装の有無を確認する。** 印象で「新しそう」と判定してはならない。
  - ライブラリなら `Gemfile` / `package.json` / lock ファイルを見て初出かを確認
  - パターンなら同種のクラス/ディレクトリ/命名を Grep して既存件数を数える
  - 既存が 1 件以上見つかれば非該当。0 件のときのみ該当。
- なぜ人間が見るべきか: 前例のないパターンは、以降のコードがそれを真似て増殖する。1 件目のレビューコストは安いが、100 件に増えてからの是正は極めて高い。技術選定は個々の PR の正しさとは別レイヤーの判断。

## T7: `high_stakes_calculation` 高リスク値計算

金額・数量・在庫・ポイント・日付境界など、誤りの影響が大きい値の**計算**の変更。

- 含まれる例:
  - 金額・税・手数料・割引・按分の計算式の変更 (係数、丸め方向、丸め桁、演算順序を含む)
  - 在庫数・残高・上限・従量課金の集計ロジックの変更
  - 有効期限・締め日・課金期間の境界判定 (`<` と `<=`、タイムゾーン、月末処理) の変更
  - 通貨・単位の変換処理、浮動小数点から `BigDecimal` などへの型変更 (結果の値が変わる場合)
  - 数値の集計対象を変える変更 (合計に含める行の条件変更)
- 含まれない例:
  - 表示フォーマットの変更 (桁区切り、通貨記号、小数点以下の表示桁数) — 計算結果の値は同一
  - 計算式のリファクタリング (説明変数の導入、メソッド抽出、定数化) で計算結果が同一のもの
  - 計算ロジックのテスト追加
  - 計算結果の受け渡し経路の変更 (変数名、引数の並び、レスポンスのキー名)
  - 金額を扱う画面のレイアウト変更・ラベル変更
- チェックポイント: **「同じ入力に対して出力される数値が変わりうるか」**。変わらないなら非該当。判断のため、丸め・境界・型に着目して変更前後の式を実際に突き合わせる。テストの期待値が変わっているかも手がかりになる (期待値が同一なら値は変わっていない可能性が高い)。
- なぜ人間が見るべきか: 1 円のずれが会計・請求・返金の実務問題になり、間違った値は既にユーザーに届いてしまう。正しい値はドメインの仕様であり、コードだけからは検証できない。

## T8: `runtime_hazard` 実行時ハザード

本番実行時に事故を起こしうる変更 — 重いクエリ、無制限のループ、ロック、外部呼び出しの増幅。

- 含まれる例:
  - 全件を一度にメモリへ載せる処理の追加 (`.all.each`、`find_each` を使わない全件ループ、ページングなしの一括取得)
  - インデックスのないカラムでの検索・ソート・JOIN の追加 (対象テーブルが大きい場合)
  - ループ内での DB クエリや外部 API 呼び出し (N+1 の新規発生)、リトライ上限のない再試行
  - 長時間ロックを取るマイグレーション (大テーブルへのデフォルト値付きカラム追加、ロックを伴うインデックス作成)
  - タイムアウト・上限件数・レート制限のない外部通信の追加
  - 同期処理として実行される重い処理 (リクエスト内で完結させる一括処理)
- 含まれない例:
  - 件数に上限のある処理 (`limit`、ページング、`find_each`/`in_batches` のバッチ処理、対象が単一レコード)
  - インデックスが存在するカラムでの検索・ソート追加 (スキーマ定義を確認して確定できる場合)
  - 対象が構造的に小さいテーブル (マスタ、設定、enum 相当) への全件アクセス
  - 既存クエリのリファクタリングで、発行される SQL の性質が変わらないもの
  - `includes`/`preload` の追加など、負荷を**下げる**方向の変更
  - 開発環境・テスト・一回限りの手動スクリプト内の重い処理
- チェックポイント:
  1. **「処理対象の件数が入力やデータ量に比例して増えるか」**。単一レコードや定数件数なら非該当。
  2. 増える場合、**「上限があるか」** — `limit`、バッチサイズ、ページング、レート制限のいずれかがあれば非該当。
  3. ソート/検索カラムについては、スキーマ定義 (`db/schema.rb`、マイグレーション、モデル) を Read/Grep してインデックスの有無を確認する。あれば非該当。
- なぜ人間が見るべきか: ステージングのデータ量では再現せず、本番の規模で初めて障害になる。「このテーブルは実際どれくらいの規模か」は運用知識であり diff の外にある。

## トリガーが重なる場合

- 1 つの変更が複数のトリガーに該当してよい。優先順位を付けて 1 つに絞る必要はない。**該当するものはすべて列挙する。**
- 例: 退会ユーザーの関連データを全件物理削除するバッチは T2 (不可逆操作) と T8 (実行時ハザード) の両方に該当する。
- **1 件でも明確に該当すれば `required`。** 該当件数は判定の強さを変えない (1 件でも 3 件でも `required`)。ただし報告では列挙する。
- 逆に、複数のトリガーに「近い」だけの変更をいくつ集めても `required` にはならない。近さは加算されない。

## 該当しないと判定してよい典型パターン

以下は、それ自体では**どのトリガーにも該当しない**。これらを理由に `required` としてはならない。

- **新規ロジック・新規条件分岐の追加** — 分岐が増えることは危険ではない。増えた分岐が T1〜T8 の領域に触れるかどうかだけが問題。
- **変更行数・変更ファイル数が多い** — 規模はトリガーではない。
- **新機能そのもの** — 機能追加は通常 `optional`。既存パターンに沿って実装され、トリガーに触れなければ該当なし。
- **UI 変更** — 見た目・レイアウト・文言の変更は該当しない (個人情報の新規表示は T4、金額の計算変更は T7 で個別に判定する)。
- **テストの追加・変更** — テストコード自体は本番で実行されない。
- **リファクタリング** — リネーム、抽出、移動、ガード節化。振る舞いが同じなら、対象がどの領域のコードであっても該当しない (T3・T7 の「含まれない例」を参照)。
- **依存ライブラリのバージョンアップ** — パッチ/マイナーは該当しない。メジャーアップで公開インターフェースが変わり外部利用者がいる場合のみ T5、初出ライブラリの導入なら T6。
- **PR 本文が薄い・説明が不十分** — 説明の質は判定の対象ではない。diff から判定する。
- **テストカバレッジが薄い** — カバレッジ不足はトリガーではない。伝えるべきことがあれば報告の「注意事項」に書く。
- **判定者がそのドメイン・技術に詳しくない** — これは判定者側の情報不足であり、PR のリスクではない。**自分の理解度を `required` の理由にしてはならない。**

最後の 3 つ (PR 本文が薄い / テストカバレッジが薄い / 判定者が詳しくない) は特に注意する。いずれも「PR について分からないことがある」状態だが、分からなさは 8 トリガーのどれでもない。トリガーを名指しできないなら `optional` である。

## pending にすべきケース / すべきでないケース

`pending` は **diff の外の事実**が判定を左右するときに限る。次の 3 条件を**すべて**満たす場合のみ:

1. 判定に必要な事実が、diff・PR 本文・リポジトリ内コードのいずれにも存在しない (Grep/Read/Glob で調べても出てこない)
2. その事実の値によって、判定が `required` と `optional` の**どちらにも転びうる**
3. 質問が、PR 作者が**事実として**答えられる形になっている (意見・判断を求める質問ではない)

pending にすべきケース:

- Webhook ペイロードから既存フィールドを削除。リポジトリ内の参照は serializer と spec のみで、**外部の受信側が存在するかがコードから分からない** (存在する → T5 該当で `required` / 存在しない → 非該当で `optional`)
- 削除処理の対象テーブルについて、バックアップ/アーカイブの運用があるかがリポジトリ内に記述されていない (ある → T2 非該当 / ない → T2 該当)
- 大テーブルへのインデックスなしソート追加で、そのテーブルの実データ規模がコードから読めない (大規模 → T8 該当 / 数百行規模 → 非該当)

pending にすべきでないケース:

- **Grep/Read で答えが出る**もの — 参照箇所、インデックスの有無、既存の類似実装、復元経路の有無。調べる前に聞いてはならない (条件 1 違反)
- **どちらの答えでも判定が変わらない**もの — 「テストは書きましたか」「動作確認しましたか」「なぜこの実装にしましたか」。答えても required/optional は動かない (条件 2 違反)
- **意見を求めるもの** — 「この設計で問題ないですか」「レビューは必要だと思いますか」。判定を作者に丸投げしている (条件 3 違反)
- **トリガー該当が既に明確**なのに確認を挟むもの — `destroy_all` が明確に追加されているのに「本当に消してよいですか」と聞く。これは `required` と判定して報告すればよい
- **トリガー非該当が既に明確**なのに確認を挟むもの — 該当を名指しできない状態で質問を作るのは、`optional` と書くのを避けているだけである

回答が得られたら、それを「diff の外の事実」として扱い再評価し、`required` か `optional` に確定させる。`pending` のまま報告を終えてはならない。
